# Confirmable Operations

Read this before changing the confirmation protocol or the storage visibility feature. Trust current source over this document. Specs: `.kiro/specs/storage-visibility-confirmation/` (the protocol) and `.kiro/specs/confirmation-dialog-copy/` (registry identity and dialog copy), each with `requirements.md`, `design.md`, `tasks.md`.

Governing skills: `understanding-sqldev` first. For SQL, follow the Supabase guidance (the `supabase` and `supabase-postgres-best-practices` skills are not installed; use the `user-postgres-dev` MCP and the migrations). For TypeScript, `tagged-unions` and `valid-state-types`.

## Why two jobs

The worker runs one DBOS workflow at a time (`packages/functions/cmd/supabaseworker/main.go`, queue `ec2-jobs`, global and worker concurrency 1). A job that waited for a human would block every other user. So waiting happens only in the browser:

1. Initiation job: validates in PostgreSQL, issues a challenge, returns `confirmation_required`, and finishes.
2. Confirmation job: a separate job that validates and consumes the challenge and appends the config row in one transaction.

Never add an `awaiting_confirmation` job status, and never park a transaction, workflow, or SQS message on user input.

## Database facts

- Migrations: the revision lives in the migrations that define each object (`20260829120003` table, guard and `d_storage_object_current_config`; `...005` views; `...007`/`20261007054500` `prepare_d_storage_upload`; `...009` notify trigger; `...010` `get_d_storage_objects`; `20261007054500` `d_storage_object_is_public`), plus `20261101090100_create_app_confirmation_protocol.sql` and `20261101090200_create_d_storage_visibility_functions.sql` (the registry identity and dialog copy are defined inside them; see \"Registry identity and dialog copy\"). There is no separate revision migration and no backfill.
- `d_storage_object_config` is insert-only. A `BEFORE UPDATE` trigger rejects updates. `DELETE` stays possible because `abort_d_storage_upload` removes the config row of an upload that never committed data, and the e2e reset truncates the table.
- "Latest config" is the greatest `config_version`, never `created_at`. `created_at` defaults to `NOW()`, the transaction start time, so a writer that waited on a lock can commit a later row with an earlier or equal timestamp. Every reader (`d_storage_object_is_public`, `d_storage_objects_base_view`, `notify_d_storage_objects_view`, `d_storage_object_current_config`) orders by revision. `UNIQUE (storage_object_id, config_version)` makes a duplicate revision impossible.
- The file `20260829120007_create_function_create_d_storage_object.sql` defines `prepare_d_storage_upload`; no `create_d_storage_object` function exists. `prepare_d_storage_upload` is the only function that creates a first config row, and it writes revision 1.
- Supabase default privileges grant `EXECUTE` on new functions (and privileges on new sequences) to `PUBLIC`, `anon`, and `authenticated`. Every internal function therefore needs an explicit `REVOKE ALL ... FROM PUBLIC, anon, authenticated`, and entry points are granted back to `authenticated, service_role` only. `CREATE OR REPLACE` keeps the existing ACL; restate it next to the definition.
- Domain outcomes are returned as tagged `jsonb`, never raised. A `RAISE` rolls back the whole job transaction, which would also undo the `active -> expired` transition that must commit. Only programming errors (NULL arguments, unregistered operation) and an invalid registry row, missing label, or invalid resolved copy raise.
- Lock order is fixed: the `d_storage_objects` parent row `FOR NO KEY UPDATE` first, then the challenge row. `FOR NO KEY UPDATE` does not conflict with the `FOR KEY SHARE` an upload insert takes through its foreign key, so uploads are not blocked. Removing the parent lock makes concurrent writers collide on the unique constraint.
- Authorization is an exact `d_storage_objects_roles.role = 'owner'` row. Do not use `authorize_d_storage_object(..., 'd_storage_objects.write')`: editors hold `write`.
- A challenge is bound to actor, `operation_kind`, target type, target id, and expected revision. The proof is 32 random bytes (43 URL-safe base64 characters); only `sha256('sqldev.confirmation.proof.v1' || chr(10) || proof)` is stored. A partial unique index allows one `active` challenge per binding. A new challenge supersedes earlier active ones in the same transaction. Expiry is `now() >= expires_at` on PostgreSQL time; the browser clock never decides.
- A challenge is consent, not authorization: `d_storage_apply_make_public` re-checks the owner role and the revision at confirmation time. A failed owner or revision check leaves the challenge `active`.

## Registry identity and dialog copy

Source: `packages/backend/supabase/migrations/20261101090100_create_app_confirmation_protocol.sql` (registry table and sequence, blank helper, immutability trigger, `app_confirmation_issue`, the resolver) and `packages/backend/supabase/migrations/20261101090200_create_d_storage_visibility_functions.sql` (`begin_d_storage_make_public`). Each object is declared once, in the migration that defines it; there is no separate registry migration. These two files were edited in place, so a database that applied the earlier versions must be rebuilt (`sqldev --stage dev supabase db reset --local` for local dev; a deployed database needs `sqldev --stage staging host data-volume replace`, because replacing only the EC2 instance keeps the data volume and the worker records applied versions in `supabase_migrations.schema_migrations` and will not re-run an edited file). The guard is `packages/functions/internal/sqldb/migration_history_test.go`: it needs no database and fails on a second declaration, a `CREATE OR REPLACE`/`ALTER`/`DROP` of these objects in another file, a `setval` in the seed, or a `*registry_id*` migration file.

- Registry identity: `registry_id` is a `BIGINT` taken from the sequence `app_confirmable_operations_registry_id_seq` (start and minimum 1000, `NO CYCLE`, owned by the column, the column `DEFAULT`). It is `UNIQUE`, `>= 1000`, `NOT NULL`, and immutable (a trigger rejects an `UPDATE` of it; copy edits stay allowed). It is presentation and protocol identity only and carries no authorization weight.
- Sequence behavior: values are allocated outside the transaction, so a failed or rolled-back insert still consumes one and identifiers are increasing but never gapless. At the maximum the next `nextval` raises, the registry `INSERT` fails, and no row changes.
- `operation_kind` stays the registry primary key and the foreign key of `app_confirmation_challenges`. Challenges bind to `operation_kind`, never to `registry_id` or to copy.
- Copy ownership: the registry columns `dialog_title_template`, `dialog_description` and `dialog_confirm_label` hold the source copy, constrained by `CHECK`s: non-blank under the Unicode `White_Space` class (`app_confirmation_text_is_blank`; do not use `btrim`, Go `TrimSpace` or JS `trim()` for this decision), a title template with exactly one `{{targetLabel}}` and no other `{{`/`}}`, description 1-2000 and confirm label 1-80 code points (`char_length` counts code points on a UTF8 database).
- `app_confirmation_resolve_dialog_copy(title_template, description, confirm_label, target_label)` is internal and `IMMUTABLE`. It builds the title with a literal single-pass `replace()` (backslashes, `&`, markup, or an embedded `{{targetLabel}}` in a name pass through unchanged), never trims, truncates or escapes, and raises one fixed message for blank text or a title over 200, description over 2000, or confirm label over 80 code points. It is the only place a title is built.
- `app_confirmation_issue` returns `challenge_id, proof, expires_at, registry_id, dialog_title_template, dialog_description, dialog_confirm_label`, all from the one registry row it reads `FOR SHARE` by the `operation_kind` the challenge binds to, so a concurrent copy edit cannot land between reading and committing. It raises fixed messages (`operation is not registered`, `registry row is invalid`) before superseding anything. Table references stay alias-qualified because the output column names are also PL/pgSQL variables.
- `begin_d_storage_make_public` keeps its signature, replay defense, guard, and grants. After the guard it reads the newest `d_storage_object_data.file_name` (`ORDER BY created_at DESC, storage_object_data_id DESC`), issues the challenge, resolves the copy, and returns `registryId` (`registry_id::TEXT`) and `dialogCopy` beside the seven earlier keys. A guard failure returns the tagged `rejected` result before any registry or label read, so an unauthorized caller learns nothing about the copy. A `RAISE` after issuance (no data row, oversized title, invalid copy) rolls back the new challenge and any supersession, so keep the label read and the resolver after the guard.
- `packages/cli/internal/e2ereset/application_reset.sql` (read by the local and staging reset) lists `app_confirmation_challenges` but not `app_confirmable_operations`, and `e2ereset/sql.go` rejects `CASCADE`, `RESTART IDENTITY`, `DROP` and `DELETE FROM` in it. The registry rows and the sequence therefore survive every e2e reset; keep the registry out of that file.

## Registering another confirmable operation

1. Add the registry row (a plain `INSERT` in a new migration; the registry table is already defined, so do not alter it). Insert `operation_kind`, `target_type`, `validity` (up to 15 minutes) and the three copy columns; omit `registry_id`, the sequence assigns it. The row must satisfy the copy `CHECK`s.
2. Add an initiation entry point that locks the target parent row, checks authorization and the revision (the guard), then reads whatever committed target data the title needs (the label), calls `app_confirmation_issue`, and passes the returned copy columns and the label to `app_confirmation_resolve_dialog_copy`. Return `registryId` as text and `dialogCopy` with the other `confirmation_required` keys. Nothing that reads registry copy or target data may run before the guard.
3. Add a branch in `confirm_app_operation` that calls an operation-specific apply function. That function locks the parent row, then `app_confirmation_lock`, calls `app_confirmation_classify`, re-checks authorization and the revision, performs the mutation, then calls `app_confirmation_consume`, all in one transaction.
4. Grant only the entry points; revoke the internals (the issue function, the resolver, the blank helper).
5. Allowlist the new functions in `packages/functions/internal/sqldb/session.go`, and add the new internal functions to `TestInternalConfirmationFunctionsAreNotCallable` (`internal/sqldb/session_test.go`).
6. Extend the contract: the `OperationKind` enum in `packages/functions/cmd/goapi/api.yaml`, the `v.OperationKind` check in `decodeOperationResult` (`api/visibility.go`, today it accepts only `StorageVisibilityMakePublic`), and `OPERATION_KINDS` in `packages/frontend/src/utils/confirmation/protocol.ts`. Regenerate and build.
7. Add a frontend adapter that holds transport and final-success behavior only (`initiate`, `confirm`, `onFinalSuccess`; see `RACCRUDTable/storage/visibility/storageMakePublicAdapter.ts`). It must hold no title, description or button label: the dialog text is the validated `ConfirmationRequired.dialogCopy`. A new operation is a registry row with its copy plus an adapter, and the host and `dialogMachine.ts` stay generic.

## Go API and worker facts

- Two routes: `POST /api/storage/buckets/{bucketName}/objects/visibility` (`visibility: public` begins make-public, `private` makes private) and the generic `POST /api/confirmations`. Both complete as a `ConfirmableOperationResult` in `JobState.result`: `confirmation_required`, `visibility_changed`, or `rejected` with a reason.
- A domain rejection is a **completed** job with HTTP 200. `Server.Finish` drops the body of any outcome with status >= 400, so a 4xx rejection would lose its reason.
- `strictJSONBody` (`router.go`) guards only those two routes. The generated handler ignores unknown JSON fields and leaves missing ones at zero. `decodeStrict` catches unknown fields at any depth but not missing ones, so executors and result decoding also call `hasExactKeys`. A missing `public` would otherwise silently mean "make private".
- `jobs.Fingerprinted` kinds store `Fingerprint(kind, body)` on the status record at creation. `submit` returns 409 `idempotency_conflict` before the queue when a key is reused with a different body. `status.Memory.Update` keeps the fingerprint like `Dynamo.Update` does.
- The status record expires after 24 hours; DBOS keeps its workflow. A reused key then yields a fresh `pending` record behind a finished workflow. `reconcileOutcome` settles it from the recorded `jobs.Outcome` (the worker stamps `Outcome.Fingerprint`) and runs nothing again; a different body becomes a completed `idempotency_conflict`.
- The proof is in the SQS body, the DBOS input/output, and the owner-scoped job result (24 h TTL, single use, 5 min validity). It is never logged and never in `Record.Message`, the fingerprint, or any status attribute.
- Adding the `Visibility` enum to `api.yaml` renamed the constants of `/notify`'s inline `visibility` enum, which broke `notify.go`; `/notify` now references the shared `Visibility` schema. That hazard is specific to enums: the string and object schemas `RegistryIdentifier` and `AuthoritativeDialogCopy` renamed nothing. Rebuild after every spec edit.
- Run `go generate` with `CGO_ENABLED=0`. Its `config.yaml` output path is relative to the working directory, so run it from `packages/functions/cmd/goapi` or it writes a stray generated file elsewhere. Never hand-edit the generated Go file.

### Result contract with registry identity and dialog copy

`ConfirmationRequiredResult` in `packages/functions/cmd/goapi/api.yaml` has nine required keys: `kind`, `registryId`, `operationKind`, `target`, `expectedRevision`, `challengeId`, `proof`, `expiresAt`, `dialogCopy`, with `additionalProperties: false`. `registryId` is a `RegistryIdentifier`: canonical decimal text of a `BIGINT` between 1000 and 9223372036854775807, a string so JavaScript keeps every value. `dialogCopy` is an `AuthoritativeDialogCopy` (`title` 1-200, `description` 1-2000, `confirmLabel` 1-80, no extra keys). No request schema and no other result schema carries presentation data.

- Generated code does not enforce the `pattern` or length limits, and `decodeStrict` accepts a missing key as a zero value. `decodeOperationResult` in `packages/functions/cmd/goapi/api/visibility.go` therefore enforces the contract in its `confirmation_required` branch: `hasExactKeys` over the nine top-level keys and over the nested `target` and `dialogCopy` key sets, `validRegistryID` (`strconv.ParseInt` base 10/64, `>= 1000`, and `FormatInt` equality, which rejects signs, leading zeros, spaces, decimals and overflow), and `validCopy` (per field: `utf8.ValidString`, at least one rune outside `isBlankRune`, and `utf8.RuneCountInString` within 200/2000/80). `isBlankRune` spells out the Unicode `White_Space` class and is not `strings.TrimSpace`; U+FEFF is not blank. Any failure becomes `outcomeError` with the generic message `invalid operation result: malformed result`, which omits the payload (it holds the proof). Invalid UTF-8 cannot reach `validCopy` through `json` (the decoder substitutes U+FFFD), so the UTF-8 check is defence in depth.
- Shared corpus `packages/functions/cmd/goapi/api/testdata/confirmable_results.json`: `valid` (nine-key results: both id bounds, exact 200/2000/80 copy in ASCII and astral characters, markup, combining and right-to-left copy, U+FEFF-only copy), `legacy` (fully valid seven-key results) and `malformed` (missing or extra keys at every level, wrong types, non-canonical `registryId` spellings including the JSON number `1000`, U+00A0-only or U+0085-only copy, over-length copy). Go decodes every `valid` entry and rejects `legacy` and `malformed`; TypeScript round trips `valid`, decodes `legacy` to `{scope: "copy", shape: "legacy"}` and `malformed` to a `protocol_error`. `valid` and `legacy` arrays hold bare results; `malformed` holds `{name, value}` pairs. Non-ASCII is `\uXXXX` escapes; never put a lone surrogate in it (Go's `json` accepts it as U+FFFD, so the bindings would disagree).
- Go tests: `TestContractPropertyThreeConfirmationRequiredWithDialogCopy` (`api/visibility_contract_test.go`) is the Go binding of Property 3: it round trips random valid results, rejects single-step drops, extras and mistypes at the top level, `target` and `dialogCopy`, and reads all three corpus sections. The generator `randomConfirmationRequired` (nine keys) is in the same file; the fixtures `requiredResult` (nine keys) and `legacyRequiredResult` (seven keys) are in `api/visibility_handler_test.go`; `visibility_copy_test.go` holds the `validRegistryID`, `validCopy` and blank-class examples. The older Property 15 `quick.Check` calls `t.Fatal` on its first bad seed, so a generator regression there hides the corpus loop that follows it.
- Replay carries the nine-key body unchanged. `operationOutcome` re-marshals the validated struct (semantically equal to the database result, not byte-equal: `<`, `>`, `&` and U+2028/9 become `\uXXXX` escapes), the body stays inline on the status record under `resultInlineLimit` (`api/submit.go`), request fingerprints cover only the request payload, and `reconcileOutcome` returns the recorded outcome as is. Editing the registry copy changes only later initiations.
- The worker-level replay test (`cmd/supabaseworker/dialog_copy_replay_integration_test.go`, Property 2, replay half) edits only the three copy columns on a committed connection, shows a fresh initiation gets the edited copy while every replay (concurrent, late, after the status record is recreated, and `reconcileOutcome` called directly) returns the recorded body with one challenge, and restores the original copy and the sequence state in `t.Cleanup`. The rig's owners need a `d_storage_object_data` row (`newOwnerNamed`) because initiation reads the file name; the job id is per idempotency key, so a conflicting body sent after the record expired overwrites that key's status record with `idempotency_conflict` (check it last); `workflowState` must wait for a finished DBOS state because the record completes inside the workflow body.

## Testing against the database

Integration tests live in `packages/functions/internal/sqldb/*_integration_test.go` and `cmd/supabaseworker` behind the `integration` build tag and need a database (the local Supabase port is `[db] port` in `packages/backend/supabase/config.toml`). `cmd/supabaseworker` runs the production path (API handler, status store, queue message, `processor.Accept`, real DBOS, `sqldb.Session`) with DBOS state in a throwaway `dbos_it_*` schema that the test drops.

```bash
SQLDEV_TEST_DATABASE_URL="<local Supabase database URL>" \
  CGO_ENABLED=0 go -C packages/functions test -tags integration -count=1 -p 1 \
  ./internal/sqldb/ ./cmd/supabaseworker/
```

Apply new migrations to a running local database with `sqldev --stage dev supabase migration up --local`; use `db reset` only when you intend to wipe local data.

- Registry tests (`confirmable_registry_*`, `confirmation_dialog_copy_*`, helpers in `confirmation_dialog_copy_helpers_integration_test.go`) must not change the registry or advance the real sequence. Run every registry write in a transaction that is always rolled back (`scratchTx`), and for inserts call `useScratchRegistrySequence`, which swaps the column `DEFAULT` to a `TEMP SEQUENCE` copied from the real one's options and state. The default is evaluated before the `CHECK`s and the primary key, so a failed insert consumes a value and a savepoint rollback leaves a gap, but an explicit `registry_id` that fails a check consumes none.
- To break a registry row on purpose, drop the `CHECK` in the rolled-back transaction and use `SET LOCAL session_replication_role = replica` for the `UPDATE`/`DELETE` (it skips the immutability and foreign-key triggers), then restore `origin` before calling `begin_d_storage_make_public` through `callInTx` (a savepoint, so a `RAISE` can be inspected afterwards).
- The shape of the registry, the resolver and `begin_d_storage_make_public` is asserted by `TestRegistryMigrationShape`, `TestDialogCopyResolverExamples` and `TestRegistryConstraintAndAllocationExamples` against the migrated database (registry writes only in rolled-back transactions). The declare-once rule over the migration files is asserted without a database by `migration_history_test.go`.
- Property tests are tagged with `copyProperty` (`Feature: confirmation-dialog-copy, Property N: ...`); the older `property` helper keeps the baseline tag. Tag a new property on the leaf test, not on a nested subtest.
- The harness's `createObject` inserts the `d_storage_object_data` row with `session_replication_role = replica` for that one transaction (using the real `prepare_d_storage_upload`), because the insert trigger calls `notify_http_post` against an unreachable URL; `createObjectViaRPC` keeps the full path covered.
- `TestInternalConfirmationFunctionsAreNotCallable` (`internal/sqldb/session_test.go`) lists the internal functions, including the resolver and the blank helper.

## Frontend and end-to-end facts

- Layout: the generic client lives in `packages/frontend/src/utils/confirmation/`: pure `transition` in `dialogMachine.ts` is the model, `confirmationStore.ts` is a non-persisted Zustand coordinator (separate from the persisted `storageTableStore`), `finalSuccessLedger.ts` guarantees one cache invalidation per committed change, `focusRestore.ts` returns focus to the trigger. A single `ConfirmationDialogHost` is mounted in `StorageCRUDTable`.
- Adapter role: transport and final-success invalidation only (`ConfirmableOperationAdapter` in `protocol.ts` is `kind`, `initiate`, `confirm`, `onFinalSuccess`; implementation `RACCRUDTable/storage/visibility/storageMakePublicAdapter.ts`). `DialogSubject` has no `label`. Dialog text comes from the validated `ConfirmationRequired.dialogCopy` (`AuthoritativeDialogCopy`), and `registryId` is a branded decimal string (`RegistryIdentifier`).
- `ProtocolError` is tagged by `scope` (`payload`, or `copy` with `shape: "legacy" | "malformed"`; every literal must name its scope). `rejected` is a `mode` union: `domain-or-request` (with `cause`) or `safe-copy-fallback` (with `error`). `expired` and `refreshing` carry the last validated `copy` but not the challenge.
- Decoder (`decodeResult.ts`): a `confirmation_required` payload with exactly the nine keys and valid values is a result; exactly the seven pre-feature keys with valid values is `{scope: "copy", shape: "legacy"}`; anything else of that kind is `shape: "malformed"`; any other kind or a non-object is `scope: "payload"`. It checks the registry id with `BigInt("1000")`/`BigInt("9223372036854775807")` calls (not `1000n` literals), lengths with `Array.from(value).length`, blankness with the explicit Unicode `White_Space` class (not `trim()`, which strips U+FEFF), and rejects lone surrogates (`JSON.parse` can produce them from escapes; the shared corpus cannot hold them).
- Safe fallback: an initiation or refresh result with `scope: "copy"` enters `safe-copy-fallback` (`dialogMachine.ts`), which covers confirmation-required results recorded before the feature existed. Only `Close` and `Get new confirmation` are offered. `FRESH_INITIATION` leaves the fallback with a new idempotency key and is accepted only from it; `controlsFor(...).freshInitiation` is enabled only there. A copy-scoped error returned for a confirmation is a `domain-or-request` `protocol_error`, never the fallback.
- `requesting` hides the confirm button because no authoritative label exists yet. `presentationFor(state)` supplies the dialog text: the validated copy for `confirmation-ready`, `confirming`, `expired` and `refreshing`, and fixed generic strings that name no operation otherwise (`confirming` is "Confirming…").
- Host (`RACCRUDTable/confirmation/ConfirmationDialogHost.tsx`): renders `presentationFor(view)` as React text children only and holds no operation text; it also prints the validated `registryId` as `Operation ID: <id>` (`registryIdFor` in `dialogMachine.ts`, `cy("confirm_dialog_registry_id")`), which `expired`/`refreshing` carry beside `copy` and which is display only. The heading is the one accessible name; `aria-describedby` and its `<p>` exist only when the description is non-null. The primary button needs both `controlsFor(...).confirm.visible` and a non-null `confirmLabel`. In `safe-copy-fallback` it shows only `Close` (Cancel, `autoFocus`) and `Get new confirmation` (`cy("confirm_dialog_fresh_initiation")`); `cy()` emits `data-cy` only for the `dev`/`staging` stages, so `bun test` cannot select by it. The render property test is `utils/confirmation/dialogCopy.property.test.tsx` (one `test` named Property 4); the make-public literal scan is in `ConfirmationDialogHost.test.tsx`.
- Do not use the shared `AlertDialog` for the host: its action button chains `close`, so the dialog would close while the confirmation job runs. The host composes `Dialog`, `Heading`, `Button`; `aria-busy` is set through the Dialog `render` prop; buttons that can hold focus use `isPending`.
- Zustand v5 selectors must return stable values; select functions one by one.
- Row keys are S3 keys: compare the `data-key` attribute instead of building a selector.
- A `MenuItem` whose `id` changes with data must be remounted with `key={id}`, otherwise React Aria throws "Cannot change the id of an item" when a refetch flips Make public to Make private while the menu is open.
- The e2e/staging reset SQL truncates without CASCADE: a new table referencing `users` must be added to `packages/cli/internal/e2ereset/application_reset.sql` and `plan_test.go`.
- `bun run build` clobbers the Vite optimizer cache under a running `astro dev` (504 "Outdated Optimize Dep", Clerk never loads). Touch `packages/frontend/astro.config.mjs` to restart dev.
- Cypress: `packages/e2et/cypress/e2e/driveVisibility.cy.ts` with `support/driveObjects.ts`; selectors are `data-cy` `dStorage_make_public`, `dStorage_make_private`, `confirm_dialog`, `confirm_dialog_confirm`, `confirm_dialog_cancel`, `confirm_dialog_refresh`, `confirm_dialog_fresh_initiation`, `confirm_dialog_status`. The spec asserts the dialog against the job result's `dialogCopy` (heading `h2[slot='title']`, the one `p:not([role='status'])`, the primary button text, `aria-labelledby`/`aria-describedby`). To simulate a recorded legacy result, intercept `GET /api/jobs/:id` and edit the parsed `res.body` **in place** (`delete body.result.registryId`, `delete body.result.dialogCopy`): assigning a new object to `res.body` inside `req.continue` is not delivered to the page. A markup-like file name must avoid `/` (object key separator) and `"` or `\` (the row selector quotes the name). An expiry-refresh check can swap the second result's `dialogCopy` for distinct text to prove the copy is replaced as a whole.
